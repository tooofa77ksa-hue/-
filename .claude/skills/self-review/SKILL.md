# self-review — المراجعة الذاتية

## متى تعمل
- قبل كل `push`.
- قبل إعلان اكتمال مهمة.
- بعد أي إصلاح لفشل CI.

## الخطوات

### 1. اقرأ الفرق كاملًا
```
git diff · git diff --staged
```
اقرأه **سطرًا سطرًا** كأنك مراجع يريد رفضه. السؤال الحاكم: **ما الذي سيجعل هذا يفشل؟**

### 2. القائمة العدائية
- **البقايا**: `console.log` · `print` · كود مُعلَّق · `TODO` غير مذكور · ملفات مؤقتة · بيانات تجريبية.
- **الحدود**: `nil`/`null` · صفر · سالب · فارغ · ضخم جدًا · نص بلغة أخرى · تزامن.
- **الأخطاء**: كل مسار فشل معالَج؟ أم صامت؟ الفشل يُغلق لا يُفتح.
- **النطاق**: هل عدّلت شيئًا لم يطلبه أحد؟ أزله.
- **الاتساق**: هل يشبه الكود جيرانه في التسمية والأسلوب؟
- **الأمان**: قيمة من الخارج بلا تحقق؟ سر؟ صلاحية زائدة؟
- **التراجع**: ما الذي يكسره هذا مما كان يعمل؟

### 3. شغّل فحوص المشروع فعليًا
ما يشغّله المساهم محليًا: lint · format --check · typecheck · اختبارات الوحدة للجزء المتغيّر.
**لا تفترض النجاح — شغّلها واقرأ المخرجات.**

### 4. في إصلاح خطأ أو فشل CI
- **أعد إنتاج الفشل أولًا**، ثم أصلح، ثم أظهر نفس الفحص أخضر.
- أضف اختبار انحدار يفشل قبل الإصلاح وينجح بعده.

### 5. أبقِ التغيير في أضيق حدوده
ما تحتاجه المهمة فقط. لا توسيع تلقائي، ولا إعادة هيكلة استطرادية.

## معايير القبول
- كل فحوص المشروع خضراء **بمخرجات شوهدت**.
- صفر بقايا تصحيح.
- كل مسار فشل معالَج أو مسجَّل عمدًا.
- الفرق لا يحوي تغييرًا خارج نطاق المهمة.
- دفعة واحدة متحقَّقة خير من ثلاث تخمينية.

## اختبارات التحقق
- `git diff --stat` ⇒ هل عدد الملفات منطقي للمهمة؟
- `grep -rnE 'console\.log|debugger|TODO|FIXME|XXX'` على الملفات المتغيّرة.
- أعد قراءة الطلب الأصلي ⇒ هل كل بند منفَّذ؟
- تخيّل أسوأ مدخل ممكن ⇒ ماذا يحدث؟

## المحظورات
- ❌ الدفع بلا تشغيل الفحوص.
- ❌ تعديل اختبار ليمر بدل إصلاح السبب.
- ❌ تخطّي أو تعطيل أو عزل اختبار للوصول إلى الأخضر.
- ❌ دفعات تخمينية متتابعة على أمل أن ينجح CI.
- ❌ إخفاء تحذير بدل معالجته.
