# safe-git — Git بأمان

## متى تعمل
- قبل أي `commit` أو `push`.
- عند تعارض دمج.
- عند الحاجة للتراجع عن تغيير.

## الخطوات

### 1. قبل أي شيء: تأكد من الفرع
```
git branch --show-current
```
- **ممنوع الالتزام على الفرع الافتراضي مباشرة.** إن كنت عليه ⇒ أنشئ فرعًا أولًا.
- إن كان لي فرع محدّد في تعليمات الجلسة ⇒ هو الوجهة الوحيدة. **لا أدفع إلى فرع آخر بلا إذن صريح.**

### 2. راجع قبل الإضافة
```
git status --short · git diff · git diff --staged
```
- أضف الملفات **بالاسم**، لا `git add -A` أعمى.
- افحص كل ملف جديد: هل يخصّ المهمة فعلًا؟ هل هو ملف مؤقت أو مبني؟

### 3. رسالة الالتزام
- سطر أول: فعل أمر، ≤ 72 حرفًا، يصف **ماذا ولماذا** لا كيف.
- جسم عند الحاجة: السبب، والقرارات، وما تُرك عمدًا.
- ذيول الإسناد المطلوبة في الجلسة تُضاف حرفيًا.
- **ممنوع** ذكر اسم أو معرّف نموذج في الرسالة أو في أي شيء يُدفع للمستودع.

### 4. الدفع
```
git push -u origin <branch>
```
- فشل شبكي فقط ⇒ أعد المحاولة 4 مرات بتراجع أسي (2s, 4s, 8s, 16s).
- فشل لسبب آخر (رفض، صلاحيات، تعارض) ⇒ **لا تعيد المحاولة عمياء**؛ اقرأ الخطأ وعالجه.

### 5. التعارضات
- ادمج الفرع الأساس داخل فرعي (merge) — لا rebase على فرع يشاركني فيه غيري.
- ملفات القفل والمولّدة: أعد توليدها بالأداة، **لا تحلّها يدويًا**.
- تعارض في نفس المنطق من الجهتين ⇒ اسأل بدل التخمين.

## معايير القبول
- الالتزام على الفرع الصحيح دائمًا.
- كل ملف في الالتزام مقصود.
- صفر أسرار (شغّل `secrets-guard` قبل الالتزام).
- الرسالة تشرح السبب لا الآلية.
- العمل المهم مدفوع قبل نهاية الجلسة (الحاويات مؤقتة).

## اختبارات التحقق
- `git show --stat HEAD` ⇒ هل كل ملف متوقع؟
- `git log --oneline -1` ⇒ هل الرسالة مفهومة لشخص لم يحضر؟
- `git status` بعد الدفع ⇒ نظيف.

## المحظورات
- ❌ `push --force` على فرع مشترك أو فرع شخص آخر.
- ❌ `rebase` / `amend` على تاريخ مدفوع يشاركني فيه غيري.
- ❌ `reset --hard` بلا التحقق مما سيضيع أولًا.
- ❌ `git add -A` بلا مراجعة `git status`.
- ❌ الالتزام على الفرع الافتراضي، أو الدفع إلى فرع غير المحدَّد لي.
- ❌ التزام ملفات مبنية أو مؤقتة أو `node_modules` أو أي سر.
- ❌ إنشاء Pull Request بلا طلب صريح.
- ❌ الدفع بعد نصف عمل يكسر البناء.
